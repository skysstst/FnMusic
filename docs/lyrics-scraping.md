# 歌词刮削 · 实现与设计说明

本文档说明「歌词刮削」是怎么做的、为什么这么做，以及改动过程中踩到的坑。
功能用法见 [README](../README.md#歌词刮削怎么用)。

## 1. 它解决什么问题

NAS 上的音乐文件不一定带歌词：可能没内嵌、旁边也没有 `.lrc`。
本功能在**本地找不到歌词**时，依次到多个外部歌词库联网取一份，命中后缓存在本机。

歌词只存在手机本地，**不写回 NAS、不改动任何原文件**。

## 3. 路由器：一次取词的完整链路

1. **先过滤**（见第 4 节）。不合格直接返回，**不联网**。
2. **按序降级**：渠道顺序按实测召回率排（QQ → 酷狗 → 酷我 → 网易云 → LRCLIB → AMLL），任一命中即返回。
3. **两轮策略**：第一轮只接受**带时间轴**的歌词（能滚动）；全部落空后，第二轮才允许退回**无时间轴的纯文本**。
   避免"某个渠道只有纯文本就先返回，用户看到不能滚动的死文本，其实再试一个就有能滚动的"。
4. **节流**：同一渠道两次请求之间强制间隔 350 ms。
5. **限流冷却**：渠道返回限流时按它给的 `Retry-After` 进入冷却，本轮跳过、不硬撞。
6. **负缓存**：所有渠道都试过且都没有 → 记录，**14 天内不再重复联网**；命中即清。
   schema 带版本号（当前 `4`），规则一改就抬版本，旧的失败结论自动作废。
7. **单飞**：同一首歌的并发请求合并为一次。

### 一个必须区分的状态：暂时不可用 ≠ 没有歌词

AMLL 的索引（约 6 MB）首次要下载。如果把它当成"这首歌没有歌词"，一次冷启动时序问题就会把唯一的逐字渠道**写进 14 天负缓存**。所以异常分了四种：

| 异常 / 返回 | 路由器的处理 |
|---|---|
| 正常返回 | 命中 |
| 返回 `null` | 确认该渠道没有 → 继续下一个 |
| `LyricRateLimitedException` | 进冷却 → **不写失败记忆** |
| `LyricSourceNotReadyException` | 跳过 → **不写失败记忆** |
| `LyricSourceException` | 跳过 → 继续下一个 |

## 4. 过滤器：先过滤，再联网

实测曲库 11,425 首里 **15.2% 是注定没有歌词的内容**（直播回放、栏目录音）。送进去有三个坏处：白跑请求、加速触发限流、把"已刮削 N 首"的统计灌水。

保留 **9,689 首（84.8%）**，过滤 1,736 首：

| 原因 | 数量 |
|---|---|
| 超长（> 8 分钟，直播 / 播客回放） | 1,294 |
| 直播 / 播客栏目（标题含栏目词） | 332 |
| 标题清洗后仍带主播名 | 41 |
| 片段过短（< 1 分钟） | 39 |
| 一句话、不像歌名 | 16 |
| 清唱 | 10 |
| 伴奏 / 纯音乐 | 3 |

> **一条容易写错的规则**：「标题里带主播名 → 判为直播话题」**必须跑在歌名清洗之后**。
> 清洗前的标题本来就带「陈一发儿」这截歌手段，在清洗前判会把整个曲库误杀（实测冤枉过 5,299 首）。改对之后只剩 41 首。

## 5. 歌名归一化

曲库歌名是人工录入的，形态很杂。清洗规则全部来自全库形态统计，改之前请先跑一遍统计。

主力规则：

| 规则 | 例子 |
|---|---|
| 去日期前缀（`16.12.15` / `20240106` / `220716` / `2024-01-06`） | `16.12.15陈一发儿-城里的月光` → `城里的月光` |
| 去开头方括号栏目块 | `【暗杠校园游】走歌人` → `走歌人` |
| 去版本说明括号 | `想你的365天 (Cover)` → `想你的365天` |
| 抹掉汉字中间的间隔号 | `但愿人长.久（修复）` → `但愿人长久` |
| **繁转简** | `淚橋` → `泪桥` |

切段规则（只在**恰好两段**时才动）：

- **不带空白的 `-`**：多是「歌手-歌名」→ 取**尾段**（实测 4,832 条 `陈一发儿-歌名` 靠它）
- **带空白的 ` - `**：多是「歌名 - 歌手」→ 取**首段**
- 词表认不全原唱时，靠形状猜：头段是 2~6 字纯汉字、或头段是不含汉字的**多词**拉丁名 → 判头段为人名

两条反直觉但重要的取舍：

- **猜不出来时原样返回，绝不乱切。** `Lo-Fi`、`X-Ray` 无条件按横线切会变成 `Fi`、`Ray`。
- **拉丁歌手那条必须卡「≥ 2 个词」。** 单词头段的 `Mad-World`、`Lonely-Christmas` 本身就是歌名里带的横线，切了会搜成 `World` / `Christmas`，比不切更糟。

## 6. 连通性自检（设置页的「测试」按钮）

每个渠道暴露一个**探针歌**（`LyricSource.probeQuery`）：

- 中文渠道统一用《晴天》/ 周杰伦 / 269 秒 —— 这首歌在各中文库里一定有；
- **LRCLIB 必须用西文歌**（《Hey Jude》/ The Beatles / 431 秒）。它是欧美库、中文覆盖低，用中文探针会误报成"渠道坏了"。

两个设计细节：

1. **点「测试」会先清掉该渠道的限流冷却。** 否则渠道一旦进冷却，冷却期内怎么点都是"被限流"，永远测不出"其实已经恢复了"。
2. **自检不写负缓存、不动取词状态**，纯只读探测。

状态共五种：`ok` / `noResult` / `rateLimited` / `notReady` / `failed`。
其中 `noResult`（能连上、接口也正常应答，但大众探针歌没词）是**最有价值的一条**——它基本等价于「渠道接口改版了」，而这正是做这个按钮的原因。

## 7. 踩过的坑（都是联网跑才暴露的）

### 7.1 接口把 `Content-Type` 写错，导致整个渠道静默失效

QQ 音乐和酷狗都踩到了，**同一个坑两次**：

- QQ 音乐：搜索返回 `application/x-javascript`、歌词返回 `text/html`；
- 酷狗：`mobilecdn.kugou.com` 返回 `text/html`，正文却是 JSON。

Dio 只按 `Content-Type` 决定要不要解析。结果响应体被原样留成字符串，代码拿到字符串当对象取字段 → 取不到 → **静默返回"没有"**，日志上看和"这个库没这些歌"一模一样。

**修法**：不依赖 `Content-Type` 嗅探，自己兜一层解码（各源里的 `_decode`）。

**为什么单测抓不到**：要真联网 + 真响应头。所以 `test/live_lyric_smoke_test.dart` 里加了一条联网冒烟：六个渠道的探针歌逐个实跑，**任何渠道对大众探针歌静默返回空即判失败**。

> 如果要用脚本探测这些接口，注意：Python 的 `requests` 会一律 `.json()`，不管 `Content-Type`——
> 所以**在 Python 里一切正常，只有跑进 App 才暴露**。调试时别被这一点骗了。

### 7.2 酷狗必须两步查询

`lyrics.kugou.com/search` 只覆盖**用户上传的第三方歌词**：`童话镇` / `后来` / `追梦人` 这类常规曲目恒返回 0 条。
正确姿势是先走 `mobilecdn` 搜歌拿 `hash`，再拿 hash 请求歌词。抽样 35 首实测：**单步 0% → 两步 94%**。

### 7.3 酷我返回的不是合法 JSON

`search.kuwo.cn/r.s` 用单引号做键、正文里带 `&nbsp;` 之类 HTML 实体，用 JSON 解析器会直接炸。
按字段正则取值，不试图"修好"成 JSON。歌词接口给的时间是**秒字符串**，要自己拼 `[mm:ss.cc]`。

联网冒烟**默认跳过**（这样 `flutter test` 才不依赖外部网络）。要真跑得显式开门：

```bash
LIVE_NET=1 flutter test test/live_lyric_smoke_test.dart
```

它真的打第三方接口，**别频繁跑**，容易触发限流。

## 9. 已知限制

1. **非官方接口会变。** 这一轮已经踩到两次 `Content-Type` 坑。渠道可插拔，坏一个不影响其他五个。
2. **网易云极易限流**，连续请求多了会被临时封。
3. **LRCLIB 在国内网络很可能连不上**，中文覆盖也低。
4. **同名歌曲可能配错版本。** 匹配是"歌名 + 歌手 + 时长"三级校验，跨歌手采纳时要求歌名完全一致且时长在容差内。宁可不匹配，也不给错的。
5. **AMLL 首装要下 6 MB 索引**，已改成后台预下载、不挡界面，但第一两首歌大概率拿不到逐字。
